# Turnos, avisos y coordinación de incidentes

## Comportamiento integrado

| Módulo | Puntos de entrada y persistencia |
| --- | --- |
| JO-00 | Contracts conserva `ITurnResolver` e `INotificationSender`. `Turns/CoordinationContracts.cs` publica la preferencia AUTO, los intervalos del calendario, el relevo y el registro de convocatoria. |
| JO-01 | La pestaña **Turnos** muestra el calendario diario en hora de Bolivia, incluidos los huecos. Cada encargado crea, edita y desactiva sus horarios y administra sus excepciones por fecha. Una excepción con horas reemplaza los intervalos propios de ese día. Las escrituras validan solapamientos en transacciones serializables. |
| JO-02 | La pestaña **Avisos** consulta la bandeja de la sesión cada dos segundos mientras está abierta. En otras pantallas activas se muestra un diálogo al recibir un aviso pendiente. La API guarda el instante de registro, la confirmación del dispositivo y la primera lectura. Un reintento de registro conserva el EventId. |
| JO-03 | AUTO comienza apagado para cada encargado. Activarlo afecta a sus nuevos incidentes con cobertura. El vencimiento queda en el incidente al abrirlo. Apagarlo cancela sus plazos pendientes. El servidor revisa los vencimientos cada segundo y resuelve el líder vigente del módulo. Si falta líder, conserva el pendiente para reintentar mientras el caso siga activo. |
| JO-04 | El coordinador propone el relevo y la persona propuesta lo acepta en **Turnos**. La API registra ambos actores e instantes. El cambio de mando y la aceptación se guardan juntos. El registro manual se usa cuando el coordinador ya convocó al líder por otro canal. Manual y AUTO comparten una única convocatoria inicial por incidente. |
| JO-05 | Las pruebas cubren el reloj a los 119 y 120 segundos, la pérdida de cobertura inicial, AUTO apagado, la cancelación de plazos, nuevos aportes, el cambio de horario y el relevo. Una prueba con contextos SQL Server independientes hace competir manual y AUTO. El ensayo HTTP reinicia un proceso real entre la lectura inicial y el aviso al líder. |

La entrega móvil usa consultas autenticadas con la app en primer plano. La app cerrada o suspendida recupera los avisos pendientes al volver. El prototipo no incluye un servicio de notificaciones push del sistema operativo.

## Reproducción en Windows

Desde la raíz, con .NET 10, LocalDB, sqlcmd y dotnet-ef disponibles:

```powershell
$env:UNIVALLE_TEST_SQLSERVER = 'Server=(localdb)\MSSQLLocalDB;Integrated Security=true;TrustServerCertificate=true'
dotnet test tests/Univalle.Emergencias.Tests -c Release -m:1
powershell -NoProfile -ExecutionPolicy RemoteSigned -File scripts/windows/Verificar-Jorge.ps1
```

El script crea una base con nombre aleatorio, usuarios y horarios de ensayo. Arranca la API en el puerto 5098, comprueba el OpenAPI, registra un incidente, reinicia la API y espera el plazo real. Después cierra su proceso y elimina exclusivamente su base temporal.

La variante Android requiere una instancia temporal con el APK abierto en **Cuenta**, sin sesión iniciada. Usa un emulador propio para la prueba. El ensayo inicia dos sesiones con credenciales temporales y guarda las capturas en esta carpeta.

```powershell
powershell -NoProfile -ExecutionPolicy RemoteSigned -File scripts/windows/Verificar-Jorge.ps1 -AndroidSerial emulator-5584 -AdbPath C:\Users\jorge\AppData\Local\Android\Sdk\platform-tools\adb.exe
```

Para iOS, la verificación integrada requiere un Mac con Xcode y una instancia de la API alcanzable desde el simulador o dispositivo. El criterio de aceptación es abrir **Avisos** como encargado, comprobar el identificador del incidente, leer la alerta y repetir la recepción con la cuenta del líder al vencer AUTO. Registrar por plataforma la diferencia entre el registro y la primera confirmación del dispositivo.
